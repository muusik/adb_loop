#+TITLE: Where a pull lands
#+DATE: 2026-11-12

One rule for where a project's =loop/pull.sh= puts the phone's files, the same on every machine and
in the container: =$XDG_DATA_HOME/<repo>/phone/=, the app's =files/= directory mirrored there, and
the project's data directory in its =.bl-mounts= so that bread_ladder's container sees the host's.
Proposed in chat on 2026-11-12, after a look at where the four Android projects' pulls had landed.
The reasoning is in /Four places/ below.

* Current (2026-11-12, the rule in pull.sh)

A project's data directory is =$XDG_DATA_HOME/<name>= (=~/.local/share/<name>=), the name being its
repository's, set as =adb_loop_name= in =loop/project.sh=; a project's own variable may name another
(=adb_loop_data=). =pull.sh= mirrors the app's files there under =phone/=, at the same path below
=files/= as on the phone: android_imu pulls =files/imu-logs/=, which lands in =phone/imu-logs/=. A
project that sets =pull_dest= itself keeps it (bsfc_mapper, whose data directory is =bsfc-logger=,
older than the rule).

In the container a directory is kept only on a mount from the host. A pull there into a directory
whose mount is the container's own root ends before it starts, with exit 2 and a pointer to
=.bl-mounts=: what it fetched would go with the container, and its prune would have deleted the
phone's copy of what it held.

| Project       | Phone                      | Host (desktop and laptop)                    | Mounted by       |
|---------------+----------------------------+----------------------------------------------+------------------|
| bsfc_mapper   | =com.tarkvaria.bsfc/files= | =~/.local/share/bsfc-logger/phone/=          | its =.bl-mounts= |
| android_imu   | =…imu/files/imu-logs=      | =~/.local/share/android_imu/phone/imu-logs/= | its =.bl-mounts= |
| sign_reader   | =…signs/files=             | =~/.local/share/sign_reader/phone/=          | its =.bl-mounts= |
| squiggle_snap | =…squiggle/files= (logs)   | =~/.local/share/squiggle_snap/phone/=        | its =.bl-mounts= |

A project that reads another's pulled files lists that project's line in its own =.bl-mounts=,
written exactly as the owner writes it: bl takes a mount listed twice the same way once, and refuses
the same directory mounted read-only by one checkout and read-write by another, so a session that
opens both (=bl --with=) would not start. android_imu does so for bsfc_mapper's (its
=core/tools/course_lever.py=).

* Four places (2026-11-12)

Before the rule, each project's pull landed somewhere else, on the desktop host:

- bsfc_mapper :: =~/.local/share/bsfc-logger/phone=, by its =.bl-mounts=, the same path in the
  container, on the desktop and on the laptop. The model the rule follows.
- android_imu :: =logs/= in the checkout, gitignored, beside the build's =build.log= and
  =installed.tsv=. Raw logs of about 220 MB an hour beside the source; a worktree has none of them,
  and a =git clean -x= takes them.
- sign_reader :: in the container =/home/node/geodata/phone/signs= (the host's
  =~/.local/share/bread_ladder/geodata=, the geo toolset's mount), elsewhere
  =~/.local/share/sign_reader/phone=. Two directories that nothing joins, depending on where the
  pull ran, and the prune deletes from the phone what either one holds.
- squiggle_snap :: by hand, into =/home/node/geodata/phone/squiggle=.

The geo toolset's mount was used because it was the one directory in those containers that
persisted, not because the files are geodata: a project that dropped the toolset would have lost
them from its sessions. Its one merit, that every geo project sees it, is had as well by a reader
listing the owner's line in its =.bl-mounts=.

Dropped: renaming bsfc_mapper's =bsfc-logger= to =bsfc_mapper=. Its data directory is named in its
docs, its CI runners' volumes and frozen =Run:= lines of its test plan; the rule leaves a project's
own =pull_dest= alone, and the table above says the one exception.
