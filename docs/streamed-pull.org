#+TITLE: A pull in a few streams
#+DATE: 2026-11-18

=pull.sh= fetches the phone's files one =adb exec-out= at a time, with md5 round trips before and
after: each file costs a shell started on the phone over the link, which for many small files is
most of the time a pull takes. =stream.sh= sends a whole plan of files in one call per bucket
(already compressed files plain, the rest through the phone's gzip), with a third call at the same
time carrying the phone's hashes, while keeping what =pull.sh='s transfers promise: whatever a
dropped link leaves is an exact prefix, and the next run goes on from it. Proposed and prototyped in
chat on 2026-11-18. Since /Step 3/ =pull.sh= sources =stream.sh= and =pull_all= runs in passes,
since /Step 5/ with no per-file way left; the projects take it up with their submodule's commit in
/Step 6/, bsfc_mapper with its =pull_fetch_first= rewritten as a =pull_seed=.

* Current (2026-11-18, pull_all in passes)

A plan is lines =from len rel=: the phone's bytes [from, from + len) of a file below =pull_remote=.
=stream_plan= splits it by =pull_compressed= into a plain bucket and a gzip bucket and makes three
calls at once: the two buckets and the hashes. A plan longer than =STREAM_PLAN_BYTES= (100 kB; the
command carries it over adb) goes in several calls one after another in each.

** Framing

For each file the phone sends a header =len from rel=, the bytes, then a line =-- TOKEN=, the token
new for each call; after the last file =-- end=. Here =read= takes the header (byte by byte from a
pipe) and =head -c= the bytes; GNU =head -c= reads no further than it needs from a pipe, so the
shell's next =read= starts at the token. A file from its start is one process on the phone (=head=),
a tail two (=tail | head=). A file that has become shorter than the plan says, or is gone, sends
fewer bytes: its token is not where it should be, the file is cut back to its size before the call
and the call ends. When a stream ends early, the token is looked for in the bytes just appended:
there, the file was short and is cut back; not there, all that came is the file's, an exact prefix.

Zero padding of a short file would keep a stream going, but cost five processes a file on the phone
instead of one; at about 11 ms a process on the Z2 Force that made the stream barely faster than one
call a file.

** Hashes

One call hashes, for each line of the plan, the phone's bytes [0, from + len), what the file here
will be: all the files in one =md5sum=. An append-only file may be growing, so its size is taken by
=stat= just before and just after; when both are the plan's end, =md5sum= read just that, else its
first bytes are hashed by themselves (=head -c | md5sum=) and that hash replaces the whole file's.
Hashing every append-only file's range took 3.3 s for 152 small files, the one =md5sum= 0.14 s.

Here each file is hashed in the background as soon as its bytes are in. Once the calls end,
=stream_verify= joins the two: hashes that agree take the file (a =.part= goes over its copy);
hashes that differ drop a =.part= or keep an append-only copy aside as =.stale= (=keep_stale=), to
be fetched again; a file whose phone hash did not come stays unverified. An append is therefore
optimistic: the copy here is no longer checked to be the start of the phone's file before its tail
is fetched, only after, which costs the tail's bytes in the rare case that it was not.

The lines of a call go into one file: =done=, =cut=, =short=, =skip= from the streams, =here= and
=phone= hashes, and the verdicts =ok=, =bad=, =unverified=; for a copy compared by hash, =check= and
its =copy= hash, and =same=, =differs= or =unchecked=.

** Passes

=pull_files= lists the phone's files and plans a pass from the sizes here: an append-only file's
tail onto its copy, any other file whole into its =.part= (one already of the phone's size only
hashed). A copy of the phone's size is left alone when =pull_same_size_is_same= says so or it is 1
MB or more; else it is compared by hash in the same calls, and fetched whole in the next pass when
it differs. A copy longer than the phone's, or an append-only one that differs, goes to =.stale=
first.

A pass that did not end clean is followed, after =phone_wait=, by a new listing and a pass planned
from what it left: a file =cut= or =short= goes on from its size, one =bad= from its start, one
=unverified= is only hashed. Each file has =pull_attempts= (3) across the passes, and three passes
in a row that bring nothing end the pull. An append whose hash never came is cut back at the end to
the size it had before, so that the next run fetches it again; an unverified =.part= stays, and the
next run hashes it.

A call has no timeout but a watchdog: once the file it is writing (a bucket's target, named by the
demuxer as each file starts; the hash call's own lines) has kept its name and size for
=ADB_LOOP_STALL= seconds (60), its adb is ended and the pass ends with what came, a line
=stalled CALL SECONDS= among its lines. Each call's adb therefore runs in the background into a
FIFO, so that its pid is known. The phone's side of an ended call runs until its next write fails.

Before the first pass a project's =pull_seed= is offered each phone file with neither a copy nor a
=.part= here, and may put a file at its target that is the start of the phone's: bsfc_mapper's
store, renamed on the phone by a format change (=samples_ecu.bin= to =samples_ecu.bin.v7=), is the
copy here under its old name, and only the rest comes. The pass hashes the whole after, as any
append, so a seed that was not the start is cut back and kept as =.stale= (or dropped, a =.part=); a
project checks first, with =phone_md5=, what it cannot lose. Only before the first: a later pass
would find the files the first fetched, the old name's new store among them, and offer those.

While the calls run, the monitor reads the pass's lines (the bytes of each file =done=) and the two
buckets' files at hand, which the demuxer names in =at/plain= and =at/gzip= with the size the target
had and the bytes to come, emptied once a file is done so that its bytes are not counted twice; the
status line names the one with the most still to come, with the files done of all.

** Measured (2026-11-18, sign_reader's files, Z2 Force on 5 GHz Wi-Fi)

| What                                   | One call a file | Streamed |
|----------------------------------------+-----------------+----------|
| 152 small files (=.tsv=, 2.2 MB)       | 8.1 s           | 3.1 s    |
| the same and 8 JPEGs, 22 MB            |                 | 3.4 s    |
| hashes of the 160 (alone, in parallel) |                 | 0.3 s    |

The 160 files matched the phone's own =md5sum=. The 3.4 s is about 6.5 MB/s, near what that link
carries; the 152 small files' 3.1 s is mostly the phone's =head= and the local hashing, about 20 ms
a file.
