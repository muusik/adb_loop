#+TITLE: adb_loop

How a development loop reaches an Android phone over adb and moves files to and from it, in POSIX
=sh=, for the projects that build an app and test it on a phone: finding the phone, pulling what the
app wrote, installing a build. What a project does with those files stays in that project.

The scripts move here one at a time from the two projects that use it, android_imu and bsfc_mapper.
So far:

- =where.sh= :: =runs_in=, the one line that says and enforces where a script runs, and the listing
  of a project's scripts by place.
- =phone.sh= :: reaching the phone: the address to use, whether it really answers, waiting for a
  link that dropped.
- =pull.sh= :: a directory of an app's mirrored here as deltas: each transfer resumes, a dropped
  link is waited for and gone on from, and old files held here byte for byte can be pruned from the
  phone.
- =install.sh= :: a build installed over the app: by fast deploy, checked by the package's update
  time, the logcat cleared, the label recorded and the app started again if it was running.

A plan, not built: the app's finished logs in git-annex, with the phone as an =adb= special remote
and two copies off the phone before a log leaves it (=docs/annex.org=).

* Using it

A project adds it as a submodule at =external/adb_loop=, by its https address so that a clone needs
no key:

#+begin_src sh
git submodule add https://github.com/muusik/adb_loop.git external/adb_loop
#+end_src

The project also keeps a =loop/project.sh=, which its scripts source first. It holds the project's
settings and checks that the library is the commit the project records. The check has to be in the
project, since the library is what may be missing or old:

| Library                                            | The check                           |
|----------------------------------------------------+-------------------------------------|
| At the recorded commit                             | says nothing, the script goes on    |
| Missing, or behind the record                      | updates it, and stops if that fails |
| Ahead of the record, or with uncommitted changes   | says so, the script goes on         |
| Anything else (diverged, behind with changes, ...) | stops and says why, with exit 2     |

A plain =git pull= that moves a submodule leaves its files old, and =git status= then reads
=modified: external/adb_loop (new commits)= as if someone had advanced it on purpose. A
=git commit -am= at that point records the old commit again, taking the move back for everyone who
pulls it. So on each machine that works on a project:

#+begin_src sh
git config submodule.recurse true
git config push.recurseSubmodules check
#+end_src

Its settings and the scripts' first lines:

#+begin_src sh
# loop/project.sh, above the check
adb_loop_address=${MY_PHONE:-}          # the address the user asked for, if any
adb_loop_default=phone.lan:5555         # else this one, in the container
adb_loop_last_address=                  # optional: a file with the phone's last known host
adb_loop_on_connect=                    # optional: a function to call once it answers
adb_loop_package=com.example.app        # the app, for install.sh
adb_loop_label_file=                    # optional: a file on the phone that gets the build's label
adb_loop_install_log=                   # optional: a file here that gets a line per install

# loop/where.sh, executable: run, it lists the scripts in loop/ by place
#!/usr/bin/env sh
# runs_in anywhere
. "$(dirname "$0")/project.sh"
. "$adb_loop_path/where.sh"

# loop/pull.sh, a script that reaches the phone
. "$(dirname "$0")/project.sh"
. "$adb_loop_path/phone.sh"
runs_in adb_client "$@"
phone_reach 3
adb shell ls /sdcard
#+end_src

A pull sets =pull_remote= and =pull_dest=, redefines the =pull_*= rules that =pull.sh= lists for its
own files, and calls =phone_reach=, =pull_ask_gzip=, =pull_all= and, unless told to keep,
=prune_phone=.

An install reaches the phone, then calls =install_apk APK LABEL=, with =am start= extras after them
for the app's restart. It returns 3 when the phone's copy is signed by another key: whether to
uninstall, which deletes the app's data, is the project's decision. =install_before_clear=, for a
project to redefine, runs before the logcat is cleared.

A script sources these before it changes directory, since =$0= is how it finds its checkout.

| =runs_in=       | In the container | Where the launcher is       | Elsewhere                   |
|-----------------+------------------+-----------------------------+-----------------------------|
| =container=     | runs             | runs again in the container | refuses, exit 2             |
| =adb_client=    | runs             | runs again in the container | runs, on this machine's adb |
| =agent_session= | runs             | refuses, exit 2             | refuses, exit 2             |
| =laptop=        | refuses, exit 2  | refuses, exit 2             | runs                        |

The launcher is bread_ladder's =bl= or =$BL_LAUNCHER=, for a project that builds in a container.
With neither, a script declared =adb_client= only needs adb on the =PATH=. ~ADB_LOOP_LOCAL_ADB=1~
makes a machine that has a launcher use its own adb.

* Tests

python3 unittest over a stub adb, with no phone and nothing to install:

#+begin_src sh
python3 -m unittest discover -s tests
#+end_src
